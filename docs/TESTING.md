# 테스트 작성 규칙

테스트를 추가하거나 고치기 전에 이 문서를 읽는다. 모듈 경계와 데이터 흐름은 [ARCHITECTURE.md](ARCHITECTURE.md), 모듈별 담당과 호출 계약은 [TEAM_DEVELOPMENT.md](TEAM_DEVELOPMENT.md), 요구사항 번호는 [FEATURE_SPEC.md](FEATURE_SPEC.md)를 따른다.

## 1. 테스트 레벨

| 레벨 | 도구 | 위치·파일명 | 검증 대상 | 실행 |
| --- | --- | --- | --- | --- |
| 단위 | Vitest (node) | `tests/unit/<src 하위 경로>/<구현파일명>.test.ts` | 파서, Store, 배치, 메타데이터 등 모듈 하나의 계약 | `npm run test:unit` |
| 통합 | Vitest (node), UI는 Testing Library (jsdom) | `tests/integration/<src 하위 경로>/<이름>.test.{ts,tsx}` | 여러 모듈 사이의 연결(App → Store → 어댑터) | `npm run test:integration` |
| 시스템 | Playwright (Chromium) | `tests/system/*.spec.ts` | 빌드 결과물을 실제 브라우저에서 실행한 기능 흐름 | `npm run test:browser` |
| 인수 | playwright-bdd (Gherkin) | `tests/acceptance/features/*.feature`, 단계는 `tests/acceptance/steps/*.ts` | 요구사항 명세의 합격 기준 | `npm run test:acceptance` |

테스트 코드는 모두 `tests/` 아래에 둔다. `src/`에는 테스트 파일을 두지 않는다.

```
tests/
├── unit/          src 폴더 구조를 그대로 따른다
│   ├── adapters/basic-mermaid-parser.test.ts   ← src/adapters/basic-mermaid-parser.ts
│   └── core/diagram-store.test.ts              ← src/core/diagram-store.ts
├── integration/   연결의 중심이 되는 src 폴더 아래에 둔다
│   ├── core/core-modules.test.ts               ← Store + Parser + Layout + 메타데이터
│   └── ui/App.test.tsx                         ← App 화면 + Store + 어댑터
├── system/        사용자 흐름 단위 *.spec.ts
├── acceptance/    features/*.feature, steps/*.ts
└── setup/         Vitest setup 파일
```

- **경로 규칙**:
  - 단위 테스트는 구현 파일과 같은 상대 경로에 둔다. `src/a/b.ts`의 테스트는 `tests/unit/a/b.test.ts`다.
  - 구현 파일을 옮기거나 이름을 바꾸면 테스트 파일도 함께 옮긴다.
- **import 규칙**: 테스트는 `../../../src/...` 상대 경로로 구현을 import한다.

레벨은 도구가 아니라 검증 대상으로 고른다.
- 한 모듈의 입력과 출력만 보면 단위 테스트다.
- 두 개 이상의 실제 구현을 조립해서 보면 통합 테스트다.
- 사용자 관점의 요구사항 문장을 그대로 확인하면 인수 테스트다.

## 2. 모든 레벨 공통 규칙

1. **성공과 실패를 함께 쓴다.** 새 기능이나 버그 수정마다 정상 경로 테스트와 실패·거부 경로 테스트를 1장의 경로 규칙에 맞는 테스트 파일에 추가한다. (AGENTS.md)
2. **공개 계약으로만 검증한다.** `contracts.ts`의 메서드와 `getSnapshot()` 결과를 검사한다. private 필드나 내부 함수를 꺼내 검사하지 않는다.
3. **타입 단언으로 실패를 숨기지 않는다.** `as any`, `as ClassDiagram` 대신 `kind`를 검사하고 실패하면 throw하는 좁히기 헬퍼를 쓴다. 예시는 [basic-mermaid-parser.test.ts](../tests/unit/adapters/basic-mermaid-parser.test.ts)의 `asClass`, `asSequence`, `asBlock`이다.
4. **오류는 위치까지 검사한다.** 미지원 문법 테스트는 예외 발생만 확인하지 않는다. `toThrow('2행')`처럼 행 번호를 포함해 검사한다.
5. **원문 보존을 검사한다.** 원문을 다루는 테스트는 사용자 주석, CRLF, 마지막 공백이 바뀌지 않았는지 `toBe`로 비교한다. 정규화한 문자열과 비교하지 않는다.
6. **실패 원자성을 검사한다.** 실패한 명령 뒤에도 스냅샷 참조(`toBe`), revision, 구독 이벤트 수가 실패 전과 같은지 확인한다.
7. **기댓값은 독립적으로 정한다.** 기댓값을 테스트 대상 코드로 계산하지 않는다. 예외는 왕복 테스트처럼 다른 경로의 결과를 서로 비교하는 경우뿐이다.
8. **현재 동작을 고정하는 테스트는 표시한다.** 명세가 정해지지 않아 지금 동작을 그대로 고정하는 테스트는 이름 끝에 `(현재 동작 고정)`을 붙인다. 명세가 확정되면 이 표시를 지우거나 테스트를 고친다.
9. **임시 처리는 남기지 않는다.** `it.skip`, `it.only`, `test.fixme`, 빈 테스트, 주석으로 막아 둔 assertion은 커밋하지 않는다. 미구현 범위는 PR 본문에 적는다.
10. **테스트 이름은 동작을 설명한다.** 새로 쓰는 테스트는 한국어 문장으로 "조건 → 결과"가 드러나게 쓴다. 예: `잘못된 코드 입력 시 마지막 정상 캔버스를 유지한다`. 기존 영어 이름은 그 파일을 고칠 때 함께 바꿔도 된다.

## 3. 테스트 케이스 도출 규칙

코드를 쓰기 전에 무엇을 테스트할지 먼저 정한다. 테스트 케이스(TC)는 감으로 고르지 않고, 아래 순서대로 요구사항에서 도출한다.

### 3.1 출발점: 기능명세 한 행

[FEATURE_SPEC.md](FEATURE_SPEC.md)의 세부기능 한 행이 TC 묶음 하나다. 행의 각 열에서 다음과 같이 TC를 만든다.

| 기능명세 열 | 만들 TC |
| --- | --- |
| 상세동작 1, 2, 3… | 번호마다 정상 TC를 최소 1개 만든다. |
| 예외의 `if)` 조건 | 조건마다 실패 TC를 1개 만든다. 오류 표시와 상태 불변을 함께 검사한다. |
| 예외의 `[고객 확정]` 수치·제약 | 경계값 TC를 만든다(3.2의 경계값 분석). |
| `(※확인 필요)`, `(※기술 확인)` | 확정 전에는 TC를 만들지 않고 [TEST_CASES.md](TEST_CASES.md)의 미정 목록에 올린다. 구현이 이미 특정 동작을 하고 있으면 `(현재 동작 고정)` TC로 쓴다. |
| 입력/출력 로직 | 기대 결과의 근거로 쓴다. 성능 수치(1초 등)는 인수 TC로 만든다. |

버그를 고칠 때는 먼저 그 버그를 재현하는 TC를 쓴다. 이 TC가 실패하는 것을 확인한 뒤에 코드를 고친다. 이 TC는 회귀 테스트로 계속 남긴다.

### 3.2 기법 선택

입력의 성격에 맞는 기법을 고른다. 한 기능에 여러 기법을 함께 써도 된다.

| 입력의 성격 | 기법 | 도출 규칙 | 이 프로젝트의 예 |
| --- | --- | --- | --- |
| 값의 종류가 나뉨 | 동등 분할 | 유효 클래스와 무효 클래스마다 대표값을 1개 이상 고른다. 무효 TC 하나에는 무효 조건을 하나만 넣는다. | 식별자 `A`, `_a`(유효) / `1A`, `사용자`, `A-B`(무효) |
| 한도·개수·길이가 있음 | 경계값 분석 | 한도가 n이면 n-1, n, n+1을 검사한다. 비어 있는 경우와 1개인 경우도 넣는다. | 객체 29/30/31개, Undo 5/6단계, 빈 원문, 마지막 줄바꿈 유무 |
| 이전 동작에 따라 결과가 바뀜 | 상태 전이 | 모든 상태와 모든 허용 전이를 한 번 이상 지나간다. 금지된 전이도 1개 이상 검사한다. | Store의 정상 ↔ 오류 상태, Undo/Redo 스택, 파서의 클래스 본문과 블록 스택 |
| 조건 여러 개가 결과를 함께 결정함 | 결정 테이블 | 조건 조합표를 만들고 결과가 다른 열마다 TC를 1개 만든다. | 오류 상태 × 선택 여부에 따른 저장·추가·색상 버튼 활성화, 파일 열기 중 편집 여부(ticket/revision) |
| 변환한 뒤 되돌림 | 왕복 | 변환 전 값과 왕복한 값을 비교한다. | parse → serialize → parse, 저장 → 열기 |
| 경험상 자주 깨지는 입력 | 오류 추정 | 아래 체크리스트에서 해당하는 항목을 모두 넣는다. | 아래 참고 |

오류 추정 체크리스트:
- 빈 문자열, 공백만 있는 입력
- CRLF와 LF 섞임, 한글, 이모지
- `__proto__`, `constructor`처럼 객체 키와 충돌하는 이름
- 중복 ID, 자기 자신을 참조하는 관계
- 매우 긴 입력, 깊은 중첩
- 같은 명령을 두 번 실행, 동일 입력을 다시 적용
- 늦게 도착한 비동기 결과

### 3.3 레벨 배분

같은 조건을 여러 레벨에서 반복하지 않는다. 조건 조합이 많은 검사는 가장 낮은 레벨에 둔다.

| 레벨 | 무엇을 맡는가 | 개수 기준 |
| --- | --- | --- |
| 단위 | 3.2 기법으로 도출한 조합 대부분 | 가장 많음 |
| 통합 | 모듈 사이 연결마다 정상 경로 1개와 실패 경로 1개 | 연결 지점 수만큼 |
| 시스템 | 사용자 흐름 하나에 TC 하나, 브라우저에서만 확인 가능한 결과 | 주요 흐름 수만큼 |
| 인수 | 합격 기준(AC) 문장 하나에 시나리오 하나 | AC 수만큼 |

인수 시나리오가 시스템 TC와 같은 흐름을 검증하게 되면 시스템 TC를 줄인다. 대신 그 흐름에서 인수 시나리오에 없는 부분(색상, 미리보기 등)만 시스템 TC에 남긴다.

### 3.4 요구사항 태그와 TC ID

모든 테스트는 단위부터 인수까지 기능명세 번호 태그(`SPEC-x.y`)를 하나 이상 가진다. 추적표는 이 태그로 자동 생성된다(3.8). 태그가 없거나 기능명세에 없는 번호를 쓴 테스트가 있으면 `npm run test:trace`와 CI가 실패한다.

| 레벨 | SPEC 태그 위치 | TC ID |
| --- | --- | --- |
| 단위·통합 | `describe` 또는 `it` 이름 끝에 `[SPEC-1.3]`. describe에 단 태그는 안의 모든 it에 적용된다. | 명세서의 UT·IT 케이스를 검증하는 테스트만 이름 앞에 `[UT-01]`처럼 붙인다. |
| 시스템 | `test(이름, { tag: ['@SPEC-1.1', …] }, fn)` | 이름 앞에 `[ST-…]` (필수) |
| 인수 | 시나리오 태그 `@SPEC-3.1` | 시나리오 태그 맨 앞에 `@AT-…` (필수) |

- **태그 고르는 법**:
  - 그 테스트의 assertion이 실제로 확인하는 기능 번호를 단다. 사전 조건으로만 거쳐 가는 기능은 달지 않는다.
  - 한 테스트가 여러 기능을 확인하면 여러 개 단다. 예: `[SPEC-3.2][SPEC-5.3]`
  - 파서처럼 지원 범위(1.3)와 오류 처리(1.2)가 섞인 묶음은 describe에 `[SPEC-1.3]`, 오류를 검사하는 it에 `[SPEC-1.2]`를 추가로 단다.
- **TC ID 형식**: 팀의 [소프트웨어 테스트 계획 및 테스트 케이스 명세서](https://app.notion.com/p/42369c9c21838147a203fe2c5e588a5a)(Notion, 원본)를 따른다. `<레벨>-<두 자리 일련번호>`이고 레벨은 `UT`(단위), `IT`(통합), `ST`(시스템), `AT`(인수)다. 예: `UT-01`, `IT-05`, `ST-02`, `AT-01`
  - 명세서의 케이스 하나를 여러 자동 테스트가 나눠 검증하면 모두 같은 ID를 단다. 예: 클래스·시퀀스 30개 렌더링 테스트 둘 다 `ST-01`
  - 명세서에 없는 케이스를 새로 만들면 그 레벨의 다음 번호를 쓰고, [TEST_CASES.md](TEST_CASES.md) 2장에 절차와 기대 결과를 등록한 뒤 Notion 명세서에도 추가한다.
  - 명세서 케이스와 자동 테스트의 대응, 자동화 범위(충족·부분·없음)는 TEST_CASES.md 1장에서 관리한다.
- **여러 기능을 지나가는 흐름**: ID는 하나만 단다. 지나가는 기능은 SPEC 태그로 모두 연결한다.
- **번호 재사용 금지**: 삭제한 TC의 번호는 다시 쓰지 않는다.

### 3.5 우선순위

| 우선순위 | 대상 | 규칙 |
| --- | --- | --- |
| P1 | `[고객 확정]` 항목, 데이터 유실 위험(원문 보존, 저장·열기, Undo), 핵심 기능(2.1 노드 이동) | 해당 기능 PR에 반드시 포함한다. |
| P2 | `[인터뷰]`, `[제안]` 항목, 오류 처리 | 기능 PR에 포함하거나, 다음 PR 번호를 미정 목록에 적는다. |
| P3 | 보조 기능, 표시 문구 | 여유가 있을 때 추가한다. |

### 3.6 기대 결과 작성

- **관찰 가능한 결과로 쓴다.** 구체적인 값으로 하나 이상 적는다. "정상 동작한다", "오류가 없다"처럼 쓰지 않는다.
  - 예: `코드에 "class Order"가 추가되고 Invoice의 x가 드래그 후 값과 같다`
- **실패 TC는 두 가지를 함께 확인한다.**
  1. 오류가 드러나는지: 행 번호가 있는 메시지, alert, 비활성 버튼
  2. 바뀌면 안 되는 것이 그대로인지: 원문, 스냅샷, 캔버스, 이력
- **사전 조건을 명시한다.** 기대 결과가 사전 조건에 의존하면 사전 조건을 TC에 적는다.
  - 예: `클래스 예제를 연 상태`

### 3.7 TC가 충분한지 확인

기능 PR을 올리기 전에 다음을 확인한다.

- [ ] 상세동작마다 정상 TC가 있다.
- [ ] 예외 조건마다 실패 TC가 있고, 실패 TC는 상태 불변까지 검사한다.
- [ ] 수치 제약마다 경계값 세 점(n-1, n, n+1)이 있다.
- [ ] 상태가 있는 기능은 모든 전이와 금지 전이 1개를 검사한다.
- [ ] 이번에 고친 버그마다 회귀 TC가 있다.
- [ ] 모든 새 테스트에 SPEC 태그를 달았고 `npm run test:trace`가 통과한다.
- [ ] 시스템·인수 TC는 TEST_CASES.md에 등록했고, `(※확인 필요)` 항목은 미정 목록에 올렸다.

### 3.8 요구사항 추적표 (자동 생성)

```sh
npm run test:coverage && npm run test:e2e   # reports/vitest.json, reports/playwright.json 생성
npm run test:trace                          # reports/test-trace.md 생성
```

- **생성 방식**: Vitest와 Playwright가 실행할 때마다 결과를 `reports/*.json`에 남긴다. `scripts/test-trace.mjs`가 이 결과와 [FEATURE_SPEC.md](FEATURE_SPEC.md)를 합쳐 추적표를 만든다.
- **추적표 내용**:
  - 레벨별 통과·실패 수
  - 요구사항(기능명세 번호, SRS 번호)별 단위·통합·시스템·인수 테스트 수와 상태
  - 기능별 전체 테스트 목록
- **커밋하지 않는다**: `reports/`는 .gitignore 대상이다. 최신 추적표는 CI 산출물에서 받는다.
- **부분 실행 주의**: `test:unit`처럼 일부만 실행하면 JSON이 그 결과로 덮어써진다. 전체 추적표가 필요하면 위 두 명령을 모두 실행한 뒤 생성한다.
- **상태 표시의 뜻**:
  - `⚠️ 테스트 없음`: 기능이 미구현이거나 TC가 빠진 것이다.
  - `인수 없음`: 단위·통합·시스템 테스트는 있지만 합격 기준 시나리오가 없다는 뜻이다.

## 4. 단위 테스트 (Vitest, node)

core는 순수 TypeScript이므로 단위 테스트는 node 환경에서 돌린다. DOM이나 브라우저 API가 필요하다면 단위 테스트 대상이 아니라는 뜻이니 통합 또는 시스템 테스트로 옮긴다.

### 모듈별 필수 항목

| 모듈 | 반드시 검사할 것 |
| --- | --- |
| Parser | 지원 문법, 미지원 문법의 행 번호 오류, parse → serialize → parse 왕복 |
| Serializer | 왕복 후 같은 모델, alias와 중첩 else 순서 |
| Layout | 기존 위치 유지, 새 노드만 배치, 삭제된 ID 제거, 30개 입력 |
| layout-metadata | 원문 보존, 손상된 JSON·버전 오류·중복 주석 진단, placement가 없는 v1 파일 복원 |
| DiagramStore | 실패 전후 정상 모델과 이벤트 수, 5단계 Undo/Redo, 새 편집 후 Redo 초기화, 동일 입력 무이벤트, 구독 해제, 스냅샷 동결 |
| FileManager | 한글·CRLF 왕복, 읽기 실패 시 열린 문서 보존 |

### describe 묶음 규칙

파서 테스트가 쓰는 분류를 다른 모듈에도 같은 이름으로 쓴다.

| describe 접두어 | 내용 |
| --- | --- |
| `smoke:` | 앱 기본 예제처럼 가장 자주 쓰는 입력이 동작하는지 |
| `블랙박스:` | 입력을 동등 분할하고 경계값을 잡아 `it.each`로 유효와 무효를 나눠 검사 |
| `상태 기반:` | 상태 전이(예: 클래스 본문 안팎, 블록 스택)를 순서대로 검사 |
| `오류 품질:` | 오류 메시지에 행 번호와 원문이 들어 있는지 |
| `왕복:` | parse → serialize → parse, 저장 → 열기 결과가 같은지 |
| `견고성·성능 상한:` | 30개 한도, 긴 입력, 깊은 중첩에서 시간과 예외 |

## 5. 통합 테스트 (Vitest + Testing Library, jsdom)

- **환경**:
  - `tests/integration/`은 vite.config.ts의 `integration` 프로젝트가 기본적으로 node 환경에서 실행한다.
  - DOM이 필요한 파일만 첫 줄에 `// @vitest-environment jsdom`을 쓴다.
  - DOM이 필요 없는 테스트까지 jsdom에서 돌리면 v8 커버리지 수치가 달라지므로 node를 기본으로 한다.
  - `tests/setup/vitest.setup.ts`가 jest-dom matcher와 cleanup을 등록한다.
- **실제 구현 사용**: 실제 Parser, Layout, Store를 조립해서 쓴다. 대체 구현(mock)은 `contracts.ts`의 인터페이스 경계에서만 쓴다. 예를 들어 `IRenderer`는 jsdom에서 Mermaid가 동작하지 않으므로 대체해도 된다.
- **요소 찾기**: `getByRole`, `getByLabelText` 등 접근성 이름으로 찾는다. CSS 선택자는 캔버스 SVG처럼 접근성 이름이 없는 요소에만 쓴다.
- **입력 방식**:
  - 사용자 조작은 `userEvent`로 한다.
  - 코드 전체를 바꾸는 경우에는 `user.type` 대신 `user.paste`를 쓴다.
  - 한 글자씩 입력하면 `classDiagram`까지만 입력된 중간 상태가 마지막 정상 상태로 남아서 결과가 달라진다.
- **테스트 사이의 상태 공유**:
  - App은 모듈 단위 `DiagramStore`를 공유한다.
  - 그래서 각 테스트는 `클래스 예제` 버튼으로 문서와 이력을 초기화한 뒤 시작한다.
  - 테스트끼리 실행 순서에 의존하지 않게 한다.
- **jsdom에서 검증할 수 없는 것**:
  - 포인터 좌표 변환, 파일 다운로드, Mermaid SVG, PNG 픽셀은 jsdom 결과를 근거로 삼지 않는다.
  - 이런 기능은 시스템 테스트로 검증한다.
  - PR에 "Vitest 통과"만으로 검증했다고 쓰지 않는다.

## 6. 시스템 테스트 (Playwright)

- **실행 전 빌드**: `npm run build`를 먼저 실행한다. 테스트는 `vite preview`로 띄운 빌드 결과에 접속한다.
- **흐름 단위로 작성**: 사용자 흐름 하나를 테스트 하나로 쓴다. 예: 편집 → 색상 → Undo → 미리보기.
- **검증 방법**: 화면 결과와 코드 텍스트(`toHaveValue`)를 함께 검증한다. GUI 조작이 원문에 반영됐는지가 핵심이기 때문이다.
- **기다리기**: 고정 시간 대기(`waitForTimeout`)는 쓰지 않는다. `expect(...).toHaveX()`의 자동 재시도로 기다린다.
- **브라우저 범위**: 기본 실행은 Chromium이다. 다른 브라우저 지원을 요구사항으로 정하면 playwright.config.ts의 `projects`에 추가한다.

## 7. 인수 테스트 (playwright-bdd)

- **언어**:
  - `.feature` 파일은 첫 줄에 `# language: ko`를 쓰고 `기능/배경/시나리오/조건/만일/그러면/그리고`로 작성한다.
  - 시나리오 문장은 사용자가 하는 일과 보는 결과만 적는다. 버튼 이름 외의 구현 용어(Store, revision 등)는 쓰지 않는다.
- **요구사항 추적**:
  - 시나리오마다 TC ID, SRS 요구사항, 합격 기준, 기능명세 번호 태그를 이 순서로 단다. 예: `@AT-02 @FR-3 @AC-3-2 @SPEC-3.1 @SPEC-2.1`
  - 요구사항이 바뀌면 태그로 영향받는 시나리오를 찾는다.
- **단계 정의**:
  - 단계 정의는 `tests/acceptance/steps/`에 둔다.
  - 같은 문장의 단계는 한 번만 정의하고 여러 시나리오에서 재사용한다.
  - 한 시나리오 안에서 단계끼리 값을 넘겨야 하면 `조건` 단계에서 초기화한다.
- **생성 파일**: `bddgen`이 `tests/acceptance/.features-gen/`에 테스트를 생성한다. 이 폴더는 .gitignore 대상이므로 직접 고치지 않는다.
- **성능 기준 측정(NFR-1)**: 1초 반영 목표는 이 레벨에서 측정한다.
  - 객체 30개를 기준으로 한다.
  - 코드 입력 시각부터 SVG가 화면에 표시된 프레임까지를 잰다.
  - 측정 조건(기기, 반복 횟수, 기준 통계값)을 시나리오 설명에 적는다.

## 8. 커버리지

```sh
npm run test:coverage   # 결과: 터미널 표, coverage/index.html, coverage/lcov.info
```

- **측정 범위**: 단위 테스트와 통합 테스트만 측정한다(Vitest v8). 시스템·인수 테스트는 코드 커버리지 대신 요구사항 추적표(3.8)로 범위를 관리한다.
- **하한선**: vite.config.ts의 `thresholds`에 있고, 미달하면 명령이 실패한다.

  | 범위 | statements | branches | functions | lines |
  | --- | --- | --- | --- | --- |
  | 전체 | 85 | 85 | 75 | 85 |
  | `src/core/**` | 95 | 90 | 95 | 95 |

- **하한선 운영**:
  - 하한선은 올리기만 한다.
  - 커버리지가 오르면 같은 PR에서 하한선도 올린다.
  - 하한선을 낮춰야 한다면 이유를 PR 본문에 적고 팀 리뷰를 받는다.
- **제외 대상**:
  - 실행 코드가 없는 `types.ts`, `contracts.ts`, `index.ts`와 진입점 `main.tsx`는 측정에서 뺀다.
  - 제외 대상을 추가할 때도 이유를 vite.config.ts 주석에 적는다.
- **원칙**: 수치를 맞추려고 assertion 없는 테스트를 쓰지 않는다.

## 9. PR 전 실행 순서

```sh
npm run typecheck
npm run test:coverage
npm run build
npx playwright install chromium   # 처음 한 번만
npm run test:e2e                  # 시스템 + 인수
npm run test:trace                # 추적표 생성과 태그 검사
```

PR 본문에는 다음을 적는다.
- 위 명령의 **실제 결과**: 통과 수, 실패 수, 커버리지 수치
- 추가한 테스트의 레벨과 대상 요구사항 태그, 추적표에서 바뀐 요구사항 행
- 테스트하지 못한 범위와 그 이유

### CI (.github/workflows/verify.yml)

PR을 열거나 갱신할 때와 main에 push할 때 두 테스트 job이 병렬로 실행되고(작업 브랜치 push는 PR 실행과 겹치므로 따로 돌리지 않는다), 끝나면 추적표 job이 실행된다. 하나라도 실패하면 병합하지 않는다.

| job | 실행 내용 | 산출물(90일 보관) |
| --- | --- | --- |
| 단위·통합 테스트와 커버리지 | typecheck → test:unit → test:integration → test:coverage(하한선 검사) | 작업 요약의 커버리지 표, `coverage-<커밋 SHA>` |
| 시스템·인수 테스트 | build → test:e2e(시스템과 인수를 한 번에 실행) | 실패 시 `playwright-report-<커밋 SHA>`(trace 포함) |
| 요구사항 추적표 | 두 job의 결과 JSON → test:trace(태그 검사) | 작업 요약의 레벨별·요구사항별 표, `test-trace-<커밋 SHA>` |

- **커버리지와 추적표 이력**:
  - 실행할 때마다 산출물 이름에 커밋 SHA를 붙여 90일 보관한다.
  - Actions 탭에서 실행을 고르면 요약 화면에서 수치를 바로 보고, Artifacts에서 리포트를 내려받는다.
  - 90일이 지나면 삭제되므로, 제출이나 보고서에 쓸 시점의 산출물은 따로 내려받아 둔다.
- **`.only` 검사**: CI에서는 `.only`가 남아 있으면 테스트가 실패한다. Vitest는 기본 동작으로, Playwright는 `forbidOnly` 설정으로 막는다.
- **실패해도 끝까지 실행**:
  - 시스템과 인수 테스트는 한 번에 실행하므로 한쪽이 실패해도 다른 쪽은 끝까지 실행된다.
  - 추적표 job은 테스트 job이 실패해도 실행되어 어떤 요구사항이 깨졌는지 보여 준다.
- **실패 분석**: 아티팩트의 `test-results/`에 있는 trace를 `npx playwright show-trace <파일>`로 열어 본다.

## 10. AI에게 테스트 작성을 맡길 때

TEAM_DEVELOPMENT.md의 공통 프롬프트 뒤에 다음 문장을 붙인다.

> docs/TESTING.md를 읽고 3장 규칙으로 기능명세에서 테스트 케이스를 먼저 목록으로 뽑아 보여 줘. 그다음 테스트 레벨을 정해. 성공과 실패 경로를 함께 쓰고, 기댓값은 구현 코드로 계산하지 마. 타입 단언 대신 좁히기 헬퍼를 쓰고 skip이나 only는 남기지 마. 실행한 명령과 실제 결과, 테스트하지 못한 범위를 구분해서 보고해.
