# 공통 편집 구조

요구사항 명세서의 UC-01(코드), UC-02(배치), UC-03(색상)과 컴포넌트 표를 기준으로 했다. 코드 변환기는 Parser와 Serializer로, 다이어그램 모델과 실행취소 관리자는 DiagramStore의 한 트랜잭션으로 연결한다.

## 상태 소유권

| 값 | 정의와 수명 |
| --- | --- |
| DiagramModel | kind가 class면 nodes·relations, sequence면 participants·steps. 모델은 React와 Mermaid를 import하지 않는다. |
| SequenceStep | message는 참여자 두 개를 참조하고 activation은 한 개를 참조한다. block의 branches가 각각 순서 있는 steps를 소유해 중첩 블록을 표현한다. |
| LayoutMap | 클래스·참여자 ID별 x/y/width/height/color/placement. 클래스 멤버는 노드 안의 문자열이다. 관계와 메시지는 독립 ID를 갖는다. |
| EditorSnapshot | 원문 source, 마지막 정상 model/layout, 오류, 단조 증가 revision, origin. 외부에 게시하는 객체 트리는 동결한다. |
| UI 전용 상태 | 선택 ID, 드래그 중 좌표, 미리보기 모드, 파일 요청 번호. 저장 및 Undo 대상에서 제외한다. |

## 변경 경로

1. 키 입력 → updateSource → 전용 주석 분리 → Parser → ID/참조/개수 검증 → LayoutEngine → 배치 검증 → 한 번 게시. 객체 이름이 같으면 같은 배치를 사용한다. 다른 다이어그램 종류나 새 파일에는 이전 문서의 배치를 넘기지 않는다.
2. 파싱 실패 시 오류와 입력 원문만 갱신한다. 잘못된 초안에서 Undo를 누르면 정상 스냅샷으로 복귀한다. 실패한 파일 열기는 호출자에 예외를 돌려주고 현재 문서 전체를 유지한다.
3. 포인터 이동은 UI의 미리보기, 놓기는 한 번의 moveNode다. 선택적 ISnapStrategy를 거친 뒤 배치 주석과 모델을 함께 게시한다. React는 useSyncExternalStore로 읽기만 한다. 같은 source는 다시 적용해도 이벤트가 없다.
   GUI의 객체 추가는 원문에 클래스 또는 참여자 선언을 덧붙이고 같은 파싱·검증 경로를 거쳐 한 번 게시한다.
4. 정상 변경 전에 기존 스냅샷을 최대 5개 보관한다. Undo 후 편집하면 Redo 이력을 비운다. 성공한 openSource는 새 문서의 이력을 시작한다.
5. 저장은 getPersistedSource → IFileManager.write, 열기는 read → openSource다. 로컬 .mmd 한 개에 코드와 배치를 담는다.
6. 편집 SVG는 좌표를 직접 사용한다. 별도 Mermaid 미리보기는 Serializer로 의미 모델을 출력한 뒤 패키지에 포함된 Mermaid.js로 SVG를 생성한다. 비동기 결과는 현재 요청일 때만 표시한다. 공식 미리보기는 Mermaid 자체 배치를 쓴다.

## 텍스트와 배치의 경계

전용 주석 한 줄은 `%% @se-uml-layout {"version":1,"nodes":{...}}`이다. 이동·색상 변경은 해당 줄만 갱신한다. 사용자 주석, 마지막 공백과 CRLF를 포함한 나머지 원문은 그대로 보관한다. Serializer는 의미 모델로 새 코드를 생성하며 원문 저장에 사용하지 않는다. 알 수 없는 문법, 버전 오류, 중복 주석은 진단한다. 이전 v1 파일에서 placement가 빠진 기존 위치는 manual로 복원한다.

클래스·참여자의 ID는 이름을 포함한다. 이름 변경은 삭제와 추가로 처리한다. 메시지·블록·관계 ID는 파싱 순서에 영향을 받아 다른 리비전의 영구 키로 사용할 수 없다. 객체 한도는 배치를 가지는 클래스 또는 참여자 30개로 해석했다. 멤버·메시지·관계까지 세어야 하는지는 팀 리뷰 사항이다.

## 지원 범위와 남은 작업

기본 문법 목록은 README, 각 모듈의 예외·비동기 계약은 TEAM_DEVELOPMENT에 있다. 드래그·색상, 코드 import, 파일 왕복, 5단계 이력, 새 객체 배치는 구현했다. 정확한 UML 기호와 activation/alt 프레임은 공식 미리보기에서 확인한다. 편집 캔버스는 관계·활성화 표기를 단순화한다. 스냅 전략과 이미지 내보내기는 인터페이스 단계다. 간선 경로 조정, 크기 조절 핸들, GUI 관계·메시지 편집, 최종 고딕 단일 32 이상 글꼴은 후속 작업이다. 1초 목표의 수용 테스트는 30개 객체에서 입력 시각부터 SVG가 표시된 프레임까지 측정한다. 현재 동기 코어만으로 이 목표를 보장하지 않는다.

개발 의존성 설치에는 네트워크가 필요하다. 설치 후 로컬 서버는 CDN·백엔드 없이 동작하도록 구성했다. 배포 사이트의 오프라인 재방문을 위한 서비스 워커는 제공하지 않는다.

## M2 배치

클래스는 기본 좌표를 먼저 표시한 뒤 번들에 포함된 elkjs의 layered 결과로 새 노드만 배치한다. 수동 이동이나 다음 편집으로 리비전이 바뀌면 진행 중인 결과는 폐기한다. 배치 완료 자체는 Undo 단계를 추가하지 않는다. 시퀀스는 참여자 선언 순서로 새 레인을 배치하고 메시지와 블록 순서를 유지한다.

M3에서 만든 꺾임점은 각 관계의 전용 Mermaid 주석으로 전달할 수 있다. 예시는 아래와 같다. 키는 routeKeys가 생성한다. 빈 points 배열은 경로 초기화를 뜻한다. M2는 위치 편집 후에도 절대 좌표 꺾임점을 유지하고 SVG 양 끝을 현재 노드에 연결한다. 꺾임점 조작 UI는 M5 범위다.

```text
%% @se-uml-route {"key":"[\"class:A\",\"-->\",\"class:B\",0]","points":[{"x":250,"y":140}]}
```
